# Windows Event Log Architecture

## 1. Definition
Windows Event Logs are central system audit records generated by the Microsoft Windows operating system. They record system, application, and security-related occurrences in a structured binary XML file format (`.evtx`). Stored natively within `C:\Windows\System32\winevt\Logs\`, these logs provide a continuous operational and historical record of endpoint activity, system health, authentications, and administrative modifications.

## 2. Event Providers
Event providers are underlying software components, system drivers, or application modules registered within the Windows operating system that emit event notifications when specific operational states or triggers occur.
* **How providers function:** When a software component executes an action (e.g., the Kernel-General provider initializing system time, or the Security-Auditing provider registering a user logon), it formats the telemetry according to a predefined manifest schema and sends it to the Windows Event Log service.
* **Examples:** `Microsoft-Windows-Security-Auditing`, `Service Control Manager`, `Microsoft-Windows-Kernel-General`.

## 3. Event Channels
An event channel is a logical container or destination path to which event providers publish their telemetry based on target audience and sensitivity. Channels allow administrators and analysts to query related events collectively rather than sifting through a single, unorganized stream of system-wide data.

## 4. Major Windows Logs
* **Application Log:** Stores events logged by applications, third-party software, database engines, and user-space utilities.
* **Security Log:** Contains security-relevant audit records, including user logons, privilege assignments, process creations, object access, and audit log state changes. Access is strictly restricted to administrative security contexts.
* **Setup:** Contains events generated during operating system installation, feature additions, driver staging, and Windows Update deployment sequences.
* **System:** Tracks core operating system events, driver failures, hardware errors, system boot/shutdown events, and service state transitions.
* **Forwarded Events:** Stores telemetry collected from remote endpoints across an enterprise network via Windows Event Forwarding (WEF) and WinRM protocols.

## 5. Event Record Structure
Each Windows Event record consists of standard metadata attributes:
* **Provider:** The registered software component or driver that published the event.
* **Event ID:** A numeric identifier mapping to a specific predefined event type.
* **Level:** The severity classification of the record (e.g., Information, Warning, Error, Critical, Verbose).
* **Time Created:** The precise timestamp marking when the event was generated by the operating system.
* **Event Record ID:** A sequential integer assigned to identify an individual record within a specific log channel.
* **Computer:** The Fully Qualified Domain Name (FQDN) or local hostname of the endpoint where the event occurred.
* **Event Data:** Context-specific key-value pairs (XML payload) containing detailed execution data (e.g., account names, process paths, logon types, IP addresses).

## 6. XML Structure
Every event record is stored under a root `<Event>` XML schema split into two primary sections:
* **`<System>` Section:** Contains universal structural metadata common to all Windows events, including `<Provider>`, `<EventID>`, `<Version>`, `<Level>`, `<TimeCreated SystemTime="...">`, `<EventRecordID>`, and `<Execution ProcessID="..." ThreadID="...">`.
* **`<EventData>` Section:** Contains target-specific parameters structured as `<Data Name="...">Value</Data>` child tags. This section holds custom operational fields like `SubjectUserName`, `TargetLogonId`, `NewProcessName`, and `IpAddress`.

## 7. Security Relevance
Windows Event Logs are essential for defensive security operations, threat hunting, and incident response:
* **Detection & Alerting:** High-value events (such as failed logons or service creation) trigger automated SIEM detection rules.
* **Forensic Reconstruction:** Logs enable analysts to build defensible incident timelines to determine how an adversary gained initial access, moved laterally, or escalated privileges.
* **Compliance & Auditing:** Regulatory standards require organizations to archive and monitor security event channels to verify compliance.

## 8. Limitations
* **Overwrite & Rotation Caps:** Logs operate on fixed allocation limits; old records are overwritten automatically once caps are reached under heavy traffic.
* **Anti-Forensics & Tampering:** Privileged threat actors can clear security event channels (Event ID 1102) or disable auditing policies.
* **Selective Auditing Gaps:** If an audit policy (e.g., Process Creation command-line logging) is disabled, the system will not record that activity.
* **Local Scope Restrictions:** Endpoint logs exist locally; without centralized SIEM forwarding, evidence is lost if an endpoint is wiped or rendered unreachable.
