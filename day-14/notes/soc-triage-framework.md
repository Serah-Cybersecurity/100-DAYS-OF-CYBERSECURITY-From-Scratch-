# SOC Alert Triage Framework & Operational Guide

## 1. Introduction & Purpose

The purpose of this framework is to establish a standardized, repeatable methodology for Level 1 (Tier 1) Security Operations Center (SOC) analysts to ingest, triage, investigate, classify, and resolve or escalate security alerts generated by enterprise Security Information and Event Management (SIEM) systems and EDR solutions.

Adhering to a standardized triage framework reduces Mean Time to Detect (MTTD), minimizes Mean Time to Respond (MTTR), and prevents analyst fatigue while maintaining high-quality documentation across all incident tickets.

---

## 2. Severity vs. Certainty Matrix

In a operational SOC environment, **Alert Severity** and **Malicious Certainty** are independent metrics:

* **Severity:** Represents the potential impact on confidentiality, integrity, or availability if the alert represents a legitimate threat.
* **Certainty:** Represents the probability that the telemetry reflects genuine malicious intent rather than system noise or benign activity.

| Severity Level | Definition | SLA Response Window | Target Handling Strategy |
| :--- | :--- | :--- | :--- |
| **Critical** | Immediate enterprise impact (e.g., Ransomware active execution, Domain Controller compromise). | $< 15$ Minutes | Immediate isolation, immediate escalation to Tier 2/IR team. |
| **High** | Potential compromise of critical assets or privileged credentials (e.g., Brute-force success, suspicious LSASS access). | $< 30$ Minutes | Rapid triage, primary focus of queue review, fast-track contextualization. |
| **Medium** | Suspicious activity on standard assets or policy violations (e.g., Failed SSH logins, unauthorized tool usage). | $< 2$ Hours | Batch triage, correlate with additional logs before escalation. |
| **Low / Info** | Informational events or low-risk policy alerts (e.g., New user added to standard group, port scan detected). | $< 8$ Hours / Shift End | Automated triage where possible; review for correlation with higher-severity events. |

## 3. The 5-Stage SOC Triage Workflow

```
   Stage 1            Stage 2             Stage 3            Stage 4           Stage 5
┌───────────┐      ┌────────────┐      ┌────────────┐     ┌───────────┐     ┌────────────┐
│ Acknowledge│ ───►│Contextualize│ ───►│ Analyze    │ ──►│ Classify  │ ───►│ Action &   │
│ & Assign  │      │ Data       │      │ Telemetry  │     │ Alert     │     │ Escalate   │
└───────────┘      └────────────┘      └────────────┘     └───────────┘     └────────────┘
```

### Stage 1: Acknowledge & Assign
1. Change ticket status from **New** to **In Progress**.
2. Assign the ticket to yourself in the SIEM or ticketing platform (e.g., Jira, ServiceNow, TheHive).
3. Verify timestamp bounds to calculate queue latency ($T_{\text{ingest}} - T_{\text{event}}$).

### Stage 2: Contextualize
Gather preliminary metadata across four core dimensions:
* **Host/Asset:** Critical Infrastructure, Domain Controller, Executive Workstation, Dev/Test Box, DMZ Server.
* **User Context:** Domain Admin, Service Account, Standard User, Contractor, System Account (`NT AUTHORITY\SYSTEM`).
* **Network Context:** Internal RFC1918 Address, External IP (Geolocate, ASN, Threat Intel reputation), Tor Exit Node.
* **Temporal Context:** Business hours vs. off-hours, scheduled maintenance window status.

### Stage 3: Analyze Telemetry
Query logs across a time window of $\pm 30$ minutes surrounding the alert trigger:
* Check process creation events (Windows Event ID 4688 / Sysmon Event ID 1).
* Inspect command-line arguments, parent-child process relationships, and hash reputations.
* Verify network activity (Sysmon Event ID 3, Firewall logs, Proxy logs).
* Examine user privilege changes (Event IDs 4720, 4728, 4732).

### Stage 4: Classify Alert
Map findings into one of the standard operational outcomes:

```
                          ┌───────────────────────────┐
                          │ Did the event condition   │
                          │        occur?             │
                          └─────────────┬─────────────┘
                                        │
                      ┌─────────────────┴─────────────────┐
                      ▼                                   ▼
                   [ YES ]                             [ NO ]
                      │                                   │
       ┌──────────────┴──────────────┐                    ▼
       ▼                             ▼            ┌───────────────┐
┌──────────────┐              ┌──────────────┐    │ False Positive│
│ Authorized / │              │ Malicious /  │    │     (FP)      │
│ Expected?    │              │ Unauthorized?│    └───────────────┘
└──────┬───────┘              └──────┬───────┘
       │                             │
    [ YES ]                       [ YES ]
       │                             │
       ▼                             ▼
┌──────────────┐              ┌──────────────┐
│BenignPositive│              │ True Positive│
│     (BP)     │              │     (TP)     │
└──────────────┘              └──────────────┘
```

* **True Positive (TP):** Malicious intent confirmed. Proceed to response/escalation.
* **False Positive (FP):** Detection logic failed or misidentified normal activity. Submit rule tuning recommendation.
* **Benign Positive (BP):** Event matched rule correctly, but activity was authorized (e.g., IT maintenance, pentest). Close with justification.
* **Inconclusive:** Insufficient telemetry available. Request additional logging or endpoint artifact collection.

### Stage 5: Action & Escalate
* **For FP/BP:** Close ticket, attach query results, document resolution notes clearly.
* **For TP:** Perform initial containment if authorized (e.g., host isolation via EDR, account lockout), draft concise incident handover summary, and escalate to Tier 2 Incident Response.

## 4. Documentation Standard & Incident Ticket Template

Every triaged alert must contain structured notes following the **SOAP** (Subjective, Objective, Assessment, Plan) operational template:

```markdown
### Incident Investigation Summary

**Ticket ID:** SEC-2026-00142
**Analyst:** Level 1 SOC Analyst
**Timestamp:** 2026-11-01 14:22:00 UTC

#### 1. Objective Findings (Data & Telemetry)
- **Alert Name:** Repeated Failed Logons Followed by Success
- **Target User:** `j.doe`
- **Target Host:** `WORKSTATION-04` (IP: 10.0.4.15)
- **Source IP:** 192.168.1.105 (Internal LAN)
- **Event IDs Observed:** 5x 4625 (Failed Logon) within 45 seconds, followed by 1x 4624 (Successful Logon) via Logon Type 2 (Interactive).

#### 2. Assessment
- **Classification:** True Positive (TP)
- **Reasoning:** Password spray / brute-force attempt originating from workstation `192.168.1.105`. The success immediately following multiple failures indicates credential compromise.

#### 3. Actions Taken & Next Steps
- [x] Host `WORKSTATION-04` network-isolated via EDR console.
- [x] Triggered domain password reset for user `j.doe`.
- [x] Escalated ticket to Tier 2 IR Team for memory forensics and persistence check on source host `192.168.1.105`.
```

## 5. Summary Checklist for Tier 1 Analysts

- [ ] **Always** check asset criticality before prioritizing.
- [ ] **Never** close an alert without attaching supporting log evidence/queries.
- [ ] **Correlate** across multiple log sources (Endpoint + Network + Identity).
- [ ] **Differentiate** clearly between False Positive and Benign Positive.
- [ ] **Escalate** promptly when confidence in a True Positive is established.
